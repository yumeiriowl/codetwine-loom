# Instruction files

By default, how to make a change is left to the model. The target repository's conventions, what to run before finishing, and what must not be touched reach the agents only through the request or an instruction file. An instruction file is a Markdown file at the top of the target repository whose text is added to one stage's instructions, marked as the repository's own instructions.

## Which stage reads which file

| Stage | File (default name) | Setting |
|---|---|---|
| The planning and change stages (`edit`, `sandbox`, `run`'s change workers) | `CODETWINE_LOOM.md` | `EDIT_GUIDE` (`--guide` for `edit` / `sandbox`) |
| The test-writing stage after the merge (the part that writes the test code) | `CODETWINE_LOOM_TEST.md` | `TEST_GUIDE` |
| Implementation refactoring after the merge | `CODETWINE_LOOM_REFACTOR.md` | `REFACTOR_GUIDE` |
| Test refactoring after the merge | `CODETWINE_LOOM_TEST_REFACTOR.md` | `TEST_REFACTOR_GUIDE` |
| Splitting the request, answering questions, merging, and deciding the test cases | none | — |

- Each stage reads **only its own file**. A missing file adds nothing, and no other file stands in for it. To have several stages follow the same convention, write it in each file.
- `AGENTS.md`, `CLAUDE.md` and similar files are **not read**. To reuse one, point the setting at it (`EDIT_GUIDE=AGENTS.md`).
- A relative path is from the target repository root. `""` reads no file. Only regular files are read; a non-default file that is missing prints a warning.
- Only the first `EDIT_GUIDE_MAX_CHAR` characters (default `40000`) of each file are used.
- **Container runs (`run`, `sandbox`, `integrate`) see only the repository**: the file must be inside it and not ignored by `.gitignore`. It need not be committed; untracked files are copied in. `edit` on the host can also read a file outside the repository.
- Where a file disagrees with the tool's own instructions, the tool's instructions win. Do not use the files to change how the tool finishes a run, which tools exist, or its limits; use settings for those.
- The stages after the merge run only in `run` and `integrate`.
- Lines starting with `# ` or `## ` are indented before they are added, so they lose their heading form (the log says `<N> line(s) of <path> read as this tool's own structure and were written plainly instead`). Use `###` headings or plain lists.

## What to write

Write short, concrete rules the model can act on. Good content:

- Conventions the code must follow that are not visible from one file (logging, error handling, naming, where new modules go)
- What must not be touched (generated files, public APIs, migrations, vendored code)
- What must be updated together with a change (a changelog, documentation, a schema)
- Libraries that may or may not be added
- For tests: the framework, where fixtures and helpers live, naming, how to mock, what tests must not do (network, sleeping, real credentials)

Avoid:

- Long explanations of the project; the agents read the code and the analysis
- Commands for the tool to run as its test or check; set `TEST_COMMAND`, `CHECK_COMMAND`, `RUN_COMMAND` instead
- Secrets, hostnames and paths of one machine

Read the repository first (its README, contributing guide, existing tests, linters' configuration) and write only what you found there or what the user told you. Show the user the files before you write them, since they become part of their repository.

## Templates

### `CODETWINE_LOOM.md` (planning and change stages)

```markdown
### How this repository is changed

### Conventions
- Library code logs with the module's `logger`; it never calls `print()`
- Errors that reach the user are raised as `AppError` from `app/errors.py`
- New modules go under `app/`; one public class per module

### Do not touch
- `app/generated/` (generated by `make codegen`)
- The public functions in `app/api.py` keep their names and arguments

### Update together
- Add one line at the top of `CHANGELOG.md` for changes users can see
- When a setting is added, add it to `docs/settings.md`

### Dependencies
- Do not add third-party libraries

### Tests
- When behaviour changes, update the tests that pin it; do not delete or weaken other tests
```

### `CODETWINE_LOOM_TEST.md` (writing tests)

```markdown
### How tests are written here

- Framework: pytest. Test files are `tests/test_<module>.py`
- Shared fixtures go in `tests/conftest.py`; reuse `tmp_config` for settings files
- Name tests `test_<what>_<condition>`
- Mock outside services with `monkeypatch`; tests never use the network or sleep
- Assert on return values and raised errors, not on log text
```

### `CODETWINE_LOOM_REFACTOR.md` (implementation refactoring)

```markdown
### Refactoring rules

- Keep functions under about 50 lines; split by step, not by size alone
- Prefer early returns over nested conditions
- Do not rename anything used outside the changed files
- Do not introduce new abstractions (base classes, registries) for one use
```

### `CODETWINE_LOOM_TEST_REFACTOR.md` (test refactoring)

```markdown
### Test refactoring rules

- Merge tests that differ only in input into one parametrized test
- Move repeated setup into fixtures in `tests/conftest.py`
- Keep every test name and what each test checks
```

## Checking that a file is read

When a stage reads a file, its log (`<output-dir>/agents/<agent>/<repo-name>/turns/*.log` for container runs, `<output-dir>/<repo-name>/turns/*.log` for `edit`) has the line `following this repository's own instructions: <path> (<N> characters)`. A file that is missing or empty is logged too, and a non-default file that is missing is a warning.
